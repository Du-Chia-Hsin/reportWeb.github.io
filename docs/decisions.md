## D-001　前端部署維持 GitHub Pages + 公開 repo

**日期**：2026-09-01
**狀態**：已定案
**對應**：PPT Issue 1「使用 github site 必須啟用 public 模式」

### 決定

廠商端 portal continue 用 GitHub Pages 部署，repo 維持 public。

### 理由

**站台本身無論如何都必須是公開的。** 廠商在外網用瀏覽器開，它就得是公開網際網路可達。
所以「public」的爭議點只在**原始碼**要不要公開，不是網站要不要公開。

**而原始碼公開不洩漏任何東西**，前提是照規格走：

- 金鑰由使用者手動輸入，不寫在程式裡
- GAS 的 `/exec` 網址知道了也沒用，每個請求都要通過金鑰查表
- 這正是從 `.exe` 改成 Web UI 的附帶好處 —— docx 原本擔心的「反組譯取得金鑰」風險，
  在這個架構下根本不存在，因為程式裡壓根沒有金鑰

唯一會出事的情況是**有人把金鑰 commit 進去**。這要靠 `.gitignore` 和 code review 擋，
跟 repo 公不公開無關 —— 私有 repo 一樣會外洩，只是晚一點被發現。

選它還有一個理由：少一個外部服務要維護。

### 已評估但未採用

| 平台 | 私有 repo 免費部署 | 未採用的原因 |
| --- | --- | --- |
| Cloudflare Pages | ✅ 頻寬無上限 | 目前沒有需要隱藏原始碼的理由 |
| Netlify | ✅ 每月 100GB | 同上 |
| Vercel | ✅ 個人用途 | 同上 |
| Claude Artifact | — | **技術上做不到**，見下 |

**Claude Artifact 為什麼不行**：Artifact 頁面跑在嚴格 CSP 下，`fetch` / `XHR` / `WebSocket`
打到任何外部主機一律被擋，而且是靜默失敗。portal 的全部工作就是呼叫 GAS，
這一步在該平台上做不了。此外觀看者需要 claude.ai 帳號，外部廠商不可能為此辦帳號。
Artifact 適合放**文件**（規格書、驗機報告、進度儀表板），不適合放產品。

### 重新考慮的條件

出現任一項就該重新評估，首選 Cloudflare Pages：

1. 公司政策明文禁止公開原始碼
2. 程式碼中開始出現不能公開的內容（內部主機名稱、專有演算法、客戶名單）
3. 需要自訂網域（GitHub Pages 也支援，但 Cloudflare 設定較單純）
4. 需要 preview deployment（PR 自動產生預覽網址）

### 連帶注意事項

- `vendor-portal/vite.config.js` 的 `base` 目前是 `/reportWeb.github.io/`，
  這是 GitHub Pages 專案站的路徑。**改用其他平台時要改回 `/`。**
- repo 是 public，`.gitignore` 必須擋掉 `.env`、任何 `*key*` 檔案。

## D-002　安全邊界：什麼可以公開、什麼不行

**日期**：2026-09-01
**狀態**：已定案
**起因**：發現 Sheet 共用權限開放期間，`Facilities` 的四把明文金鑰隨資料一起可被匿名讀取。

### 決定

#### 1. Sheet 永遠是私有的

共用設定固定為「限制存取」。**這是唯一的存取防線** ——
Sheet ID 是識別碼不是憑證，私有時拿著完整網址也只會得到 401。

任何「臨時開放給某人看一下」都必須在看完後立刻關閉，並視同金鑰外洩處理（見第 4 點）。

#### 2. 前端不放 Sheet ID 或網址

瀏覽器只跟 GAS `/exec` 說話，從不直接碰 Sheet；GAS 以擁有者身分讀取。
前端沒有任何理由需要 Sheet 網址，放了只是多開一個攻擊面。

**文件也適用。** repo 是公開的，Sheet ID 不寫進任何 commit 進去的檔案。

#### 3. GAS `/exec` 網址公開是設計如此

瀏覽器要呼叫它，它必然出現在前端 JS 裡，藏不掉，**也不需要藏**。
它的安全性來自金鑰驗證，不是來自隱蔽。因此 GAS 端兩條規則不可鬆動：

- **每一個 action 都驗金鑰，包含讀取。** 不因為「只是讀」而跳過
- **驗不過就回錯，不回任何資料。** 「金鑰不存在」與「金鑰無權限」統一回 `INVALID_KEY`，
  不要分開講 —— 區分開來等於告訴攻擊者哪些金鑰是有效的

#### 4. 金鑰存 SHA-256 hash，不存明文

`Keys` 分頁存 hash。GAS 收到金鑰後算 hash 比對：

```javascript
function hashKey(apiKey) {
  return Utilities.base64Encode(
    Utilities.computeDigest(Utilities.DigestAlgorithm.SHA_256, apiKey)
  );
}
```

**不需要 salt，也不需要 bcrypt。** 金鑰是 16 碼 base36 隨機字串（約 83 bits 熵），
不是人選的密碼，沒有字典攻擊或彩虹表的風險。純 SHA-256 是 API token 的標準做法，
上 bcrypt 只會讓每次請求都變慢。

**代價：管理者無法回查金鑰。** 廠商弄丟只能重發。這是正確的操作習慣，
但要事先講清楚，否則第一次遇到會被當成 bug。

搭配一欄 `金鑰提示` 存最後 4 碼（例 `…6f4`），
讓管理者能在不儲存金鑰的前提下辨識是哪一把、跟廠商核對。

#### 5. admin 金鑰只存在內部

CLI 用的 admin 金鑰權限遠大於廠商金鑰（可讀寫全部、可刪除），
**永遠不進前端、不進 repo**，只存在內部伺服器的設定檔，且該設定檔在 `.gitignore` 內。

### 判斷準則

新增任何常數前先問：**這個值外流，攻擊者能做什麼？**

| 值 | 外流後果 | 可否進 public repo |
| --- | --- | --- |
| GAS `/exec` 網址 | 能打端點，每次被金鑰擋 | ✅ |
| Sheet ID | 私有 Sheet 回 401 | ⚠️ 無害但沒必要，不放 |
| 廠商金鑰 | 讀走該廠商全部資料 | ❌ |
| admin 金鑰 | 讀寫刪除全部資料 | ❌ |

### 金鑰外洩時的處理

1. 立刻將該列 `啟用狀態` 取消勾選（不要刪列，保留稽核紀錄）
2. 產生新金鑰，寫入新 hash 與新 `金鑰提示`
3. 透過既有管道交付廠商，**不要走 email 或聊天軟體明文傳送**
4. 在 `備註` 記錄重發原因與日期

### 待辦

- GAS 端點任何人都能呼叫，可被灌流量打爆每日配額。
  目前不處理，但上線前需評估（依 IP 或金鑰做頻率限制）。

## D-003　權限模型：參與制

**日期**：2026-09-01
**狀態**：已定案
**取代**：`schema-spec.md` v1 的「專案制」（金鑰綁項目，廠商看得到整個專案）

### 決定

**廠商看得到的，是與自己相關的議題，不是整個專案。**

金鑰只綁廠商代碼，不綁項目。廠商登入後看到的專案分頁，
由「他看得到的議題」反推而來 —— 有 DFM 的議題就長出 DFM 分頁。

### 權限規則

```
可見 = 參與者.includes(金鑰對應的廠商代碼)
```

- **比對代碼，不比對名稱**
- **精確相等，不做子字串比對。** 中文廠商名共用字太常見
  （「稻禾」與「禾宇」比對「禾」會互相命中），子字串比對遲早出事
- `提出者` / `責任單位` / `參與者` 一律存代碼，由 `Parties` 分頁做資料驗證。
  自由文字輸入會讓打錯字變成「靜默失去存取」，這種 bug 極難追查 ——
  使用者只會說「資料不見了」

### `參與者` 欄位

由 GAS 維護，**append-only**：每次寫入時把 `提出者` 與 `責任單位` 的代碼
加入此欄（已存在則略過），**永不移除**。人不手動編輯。

正常流程下它等同 `{提出者, 責任單位}` 的複本，不影響任何行為。
它存在的唯一理由是失效模式的選擇：

| 情境 | 無此欄 | 有此欄 |
| --- | --- | --- |
| 有人誤改 `責任單位` | 舊廠商立刻失去存取，連自己寫的處理方式都看不到 | 舊廠商保有讀取權 |

「誤改後舊廠商多看到一點」明顯優於「誤改後舊廠商丟失自己的工作紀錄」。

內部單位代碼（如 `AE01`）也會進入此欄，無害 ——
沒有任何廠商金鑰對應到內部代碼，不會因此獲得存取權。

### 業務規則：轉手 = 結案 + 開新議題

議題轉手給另一家廠商時，**不是修改 `責任單位`**，而是：

1. 原議題 `目前狀態` 改為 `已結案`，`處理方式` 註明移交對象
2. 新廠商開立新議題

好處：

- 每家廠商的工作範圍有明確起訖
- `實際結案日` 有意義 —— 是真的完成或移交，不是被改到消失
- 稽核軌跡自然形成，兩筆都查得到

`參與者` 是這條流程被繞過時的安全網，不是替代品。

### 已知後果

**1. 廠商看到的統計數字與內部不同。**

參與制下，純內部議題（提出者與責任單位都是內部單位）廠商看不到，
所以廠商端的「議題總數」必然小於內部端。開會對數字時會兜不攏。

**對策是文案，不是邏輯**：廠商端一律標示「**與您相關的議題**：4」，
不要只寫「議題總數：4」。這一行字省下的解釋成本遠大於它的成本。

**2. 跨廠商議題兩家都看得到。**

`提出者` = 稻禾、`責任單位` = 亞瑟的議題，兩家都看得到。
在參與制語意下這是正確行為（兩家都相關），但要意識到
廠商之間會知道對方參與了哪些議題。若日後有隔離需求，需另行設計。

**3. 專案 metadata 的可見範圍。**

廠商只要有一筆該專案的議題，就會看到該專案的 `專案名稱` / `設備名稱` 等資訊。
目前視為可接受（沒有這些資訊議題無法理解）。
